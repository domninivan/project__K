# Совместная работа

Работа ведётся в GitVerse: задача → ветка → запрос на слияние → независимое ревью → проверка результата. Владельцы компонентов и документов указаны в [TEAM.md](TEAM.md) и [RACI](docs/07-raci.md).

1. Укажите требование R, пакет WBS, исполнителя, зависимости и критерии готовности. Используйте [шаблоны](docs/templates/). Оценка и согласованный срок хранятся в задаче; прогноз не выдаётся за обязательство.
2. Создайте ветку от актуальной основной ветки: `feature/short-name`, `fix/short-name`, `docs/short-name`. Для текущего переноса используется `feature/docs`.
3. Изменяйте только свой компонент и согласованные контракты. Миграции Java ведёт Бульдин, Go — Домнин; интеграционные поля согласуются с Ручкиной, обмен 1С — с Корепановой.
4. Выполните применимые [проверки](tests/README.md), обновите документы и приложите фактический результат. Невыполненные и заблокированные проверки перечислите явно.
5. Подготовьте запрос по [шаблону](docs/templates/pull-request.md): проблема, результат, связанная задача, способ проверки и ограничения. Другой участник проводит ревью; собственный компонент автор единолично не принимает.
6. После исправлений и согласования выполните слияние и обновите задачу. В этой сессии документационные изменения оставляются без коммита для проверки пользователем.

## Изменения требований и контрактов

Изменение API включает маршруты, поля/типы, время и timezone, ошибки, версии, повторы и конкурентные команды. Вместе с изменением обновляйте пример запроса/ответа, матрицу R → задача → тест и приёмочный сценарий. Прямой доступ React к Go и запись в чужую БД противоречат целевой цепочке.

Изменения объёма согласуют автор, владелец A по RACI и Бульдин. Решение с датой и влиянием на сроки фиксирует [реестр изменений](docs/13-project-management.md). R33–R39 требуют отдельного плана; добавление документа не расширяет Must.

## Готовность результата

- Критерии задачи выполнены; незавершённое описано.
- Проверки привязаны к версии кода, среде, данным и доказательству.
- Обновлены затронутые требования, архитектура, ADR, инструкции и трассируемость.
- Получено независимое ревью; при невозможности порядок проверки согласован с куратором.
- Нет секретов и реальных чувствительных данных; примеры синтетические.

README компонентов объясняют расположение кода и запуск; `docs/04-progress.md` хранит контрольные точки, а не ежедневный дубль трекера. Итоги чатов переносятся в GitVerse не позднее следующего рабочего дня. Корепанова собирает статусы еженедельно и за два дня до занятия; просрочку исполнитель сразу сообщает ей и Бульдину. Полный [регламент](docs/13-project-management.md) сохраняет порядок коммуникаций и эскалаций.

Указывайте происхождение сторонних данных, кода и сгенерированных материалов и выполненные проверки. Используйте вымышленные данные. Не публикуйте `.env`, пароли и токены.
