# Проверки проекта

Координатор QA — Домнин. Разработчики проверяют свои компоненты; Go ревьюит другой участник, по программе — Бульдин. Успешный прогон текущей версии не подтверждён: ниже команды и план, а не результаты выполнения.

## Автоматические проверки

Команды выполняются из корня в PowerShell, при установленных зависимостях соответствующего компонента:

```powershell
Push-Location GoBackend
go test ./...
Pop-Location
Push-Location JavaBackend/production-java-backend
.\mvnw.cmd test
Pop-Location
Push-Location Frontend
npm run build
Pop-Location
```

Go содержит unit-тесты config, model, service, handler и middleware. Java содержит проверки XML, JWT, регистрации, ролей, доступа к заказам и миграций. PostgreSQL-тесты запускаются только при заданной JAVA_MIGRATION_TEST_URL; также задайте JAVA_MIGRATION_TEST_USER и JAVA_MIGRATION_TEST_PASSWORD для отдельной тестовой БД. Они создают тестовые данные: рабочую БД использовать нельзя. Без URL эти проверки пропускаются, поэтому успешный Maven test сам по себе не доказывает проверку сценариев с БД. Frontend `npm test` печатает `No tests configured yet`; это заглушка. Сборка Vite проверяет сборку, а не поведение UI.

Дополнительные проверки Bash: `bash tests/init-java-env.sh` (временные файлы .env)
и `bash tests/java-baseline-check.sh` (отдельный PostgreSQL с CREATEDB; переменные
BASELINE_TEST_ADMIN_URL, DB_USERNAME, DB_PASSWORD). Эти скрипты запускаются из корня
в Linux/Dev Container. Для проверки init используется одноразовый Docker-контейнер,
как описано в `docs/15-local-development.md`.

## Ручные и приёмочные проверки

[Полная программа T-01–T-27, наборы F и риски](../docs/11-acceptance-and-risks.md) сохраняет шаги, ожидаемые результаты, методику и протокол. [Матрица](../docs/14-traceability.md) связывает проверки с требованиями. T-21–T-27 отложены после MVP.

| Область | Действия | Ожидание и ограничение |
| --- | --- | --- |
| Локальный UI | Открыть изделия и заказы; создать заказ с несколькими позициями | Новый заказ отображается в памяти; после перезагрузки не сохраняется. Это не API-тест. |
| Go health | GET `http://localhost:8081/api/v1/live` и `/api/v1/ready` | Live показывает живой процесс, ready проверяет готовность БД. |
| Рабочие центры | GET/POST `/api/v1/work-centers` на синтетических данных | Корректное создание/список и отклонение некорректного ввода; запросы в коллекции Bruno. |
| Java изделия/заказы | Выполнить GET `/api/products`, POST/GET `/api/orders` по DTO | Сохранение шапки/позиций, валидация и логическая отмена; контакты пока отсутствуют. |
| Планирование и 1С | Сценарии программы после согласования API | Сейчас заблокированы отсутствующими Go API и реализацией обмена 1С. |

Подготовка стенда: [локальная разработка](../docs/15-local-development.md). Коллекции [Bruno__K](../Bruno__K/) проверяйте по фактическим маршрутам: наличие коллекции не означает её актуальности или успешного выполнения.

Для планировщика обязательны проверки последовательности, календарных окон, отсутствия пересечений, конечного отказа при нехватке мощности, повторных и параллельных запросов. Производительность: по программе фиксируются стенд, размер набора, три прогрева и десять замеров, min/median/max; критерий 5 секунд требует согласованных условий.

## Фиксация результата

После реального выполнения создайте `tests/results/RUN-ID/` с commit, датой/часовым поясом, версиями компонентов/миграций/набора, конфигурацией стенда, исполнителем и ревьюером. Для каждого T запишите фактический результат, статус и доказательство (запрос/ответ, журнал, снимок БД); для дефекта — DEF-ID, исправление и повторный прогон. Эти каталоги создаются при прогоне, пустые отчёты не являются результатами.

Статусы: запланировано, успешно, неуспешно, заблокировано, отложено. Частичное выполнение не закрывает весь T. Будущий этап не входит в процент приёмки MVP. Текущие ограничения и разрывы перечислены в [архитектуре](../docs/03-architecture.md).
