# Миграции Java и роли

При запуске JavaBackend бин `javaFlyway` из `applicationContext.xml` вызывает
`migrate` на существующем XML DataSource. `sessionFactory` зависит от завершения миграций: сначала
обновление схемы, затем Hibernate validate. Стандартная автоконфигурация Flyway
отключена, чтобы не запускать миграции вторым механизмом.

Скрипты находятся в `src/main/resources/db/migration`:

- V1 — исходная схема Java.
- V2 — таблица `app_user` и ограничение пяти допустимых ролей.
- V3 — владелец заказа: nullable client_id для явного переноса старых записей.
- V4 — прежние демонстрационные изделия, операции, материалы, заказы и позиции.

На пустой БД выполняются V1–V4. Docker создаёт только БД PostgreSQL и хранит её
в томе. SQL init-скриптов в Compose больше нет: единственный механизм создания
и обновления Java-схемы и наполнения — Flyway при запуске JavaBackend.
Повторный запуск не повторяет выполненные миграции. V4 сохраняет ранее внесённые
демоданные: использует ON CONFLICT и проверку комментариев DEMO_ORDER_001/002.
Демозаказы без владельца доступны только планировщику; пользователи и пароли
автоматически не создаются.

## Первый запуск на существующей базе

Сделайте резервную копию и убедитесь, что подключение указывает на Java-БД,
а её исходная схема соответствует `src/main/resources/db/migration/V1__initial_schema.sql`.
Это относится только к старой Java-БД без `flyway_schema_history`. Baseline не проверяет
соответствие старой схемы и не предназначен для произвольной базы.

На один первый запуск задайте `JAVA_DB_BASELINE_ON_MIGRATE=true`.
Flyway зарегистрирует существующую схему как версию 1 без повторного создания
таблиц, затем выполнит V2–V4. После успешного запуска уберите переменную.
По умолчанию baseline выключен: непустая БД без истории миграций приводит
к остановке запуска, а не к неявному принятию неизвестной схемы.

Flyway ведёт `public.flyway_schema_history`. Применённые скрипты не менять;
следующее изменение оформляется отдельной миграцией V5 и далее. Очистка схемы
через Flyway запрещена конфигурацией. Обычные перезапуски пропускают уже
выполненные версии.

Если история Flyway уже есть (например, выполнены V1–V3), baseline не включать:
при обычном запуске будет выполнена только V4. Существующие тома и данные не удалять.
Для новой пустой БД также не включать baseline: Flyway сам выполнит всю цепочку.

## Роли

У пользователя одна роль: CLIENT, PLANNER, SHOP_MANAGER, WORKER или REPORTING.
Значения определены enum `Role` и CHECK таблицы `app_user`. Сущность `AppUser`
содержит Long ID, имя, уникальный логин, хеш пароля, роль и active.
Миграция создаёт пустую таблицу: общих паролей и автоматически назначенных
владельцев старых заказов нет.

JWT, login, права существующих API и правила владельцев описаны в `AUTH.md`.

## Проверка

Сборка: `./mvnw test` (Windows: `.\mvnw.cmd test`).
Для PostgreSQL-проверок задайте `JAVA_MIGRATION_TEST_URL`,
`JAVA_MIGRATION_TEST_USER`, `JAVA_MIGRATION_TEST_PASSWORD`. Нужна отдельная
тестовая БД с правом CREATE SCHEMA. MigrationTest создаёт уникальную схему и удаляет
только её после выполнения. AuthPostgresTest запускает приложение и создаёт
данные в public тестовой БД. Без URL PostgreSQL-тесты пропускаются.
