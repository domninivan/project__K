# Frontend

Интерфейс производственных заказов на React + Vite. Все команды ниже выполняются из папки `Frontend`.

## Запуск и сборка

```bash
npm install
npm run dev
```

Открыть http://localhost:5173. Для сборки: `npm run build`, результат в `dist/`.

## Страницы и деморежим

- `/orders` — список заказов; `/` перенаправляет сюда.
- `/orders/new` — пустая форма, открывается кнопкой «+ Создать заказ».
- `/products` — таблица изделий.

Выберите изделие, добавьте позицию, укажите количество и дату, затем нажмите «Создать заказ». Откроется карточка созданного заказа; заказ также появится первым в списке. «Отмена» и «← К заказам» возвращают в список без создания.

По умолчанию включён деморежим (`mock`): HTTP-запросов нет, заказы хранятся только в состоянии React, перезагрузка возвращает две исходные болванки. В режиме `api` данные загружаются из Java backend — см. следующий раздел.

## Подключение к Java API (режим api)

Режим выбирается переменной `VITE_DATA_MODE` (по умолчанию `mock`):

- `mock` — деморежим: данные из `src/mocks/mockData.js`, HTTP-запросы не выполняются; создание заказа и согласование плана работают в памяти, отмена через API недоступна.
- `api` — каталог и заказы загружаются из Java backend, создание и отмена выполняются через HTTP-клиент.

Для работы в режиме `api`:

1. Запустить Java backend на порту 8080:
   ```bash
   cd JavaBackend/production-java-backend
   ./mvnw spring-boot:run
   ```
2. Создать `Frontend/.env` по образцу `.env.example`:
   ```
   VITE_DATA_MODE=api
   JAVA_API_TARGET=http://localhost:8080
   ```
3. Перезапустить Vite — переменные окружения читаются только при старте.

Запросы `/api/*` проксируются на `JAVA_API_TARGET` (настройка в `vite.config.js`, префикс `/api` сохраняется). HTTP-клиент — `src/api/httpClient.js`, функции — `src/api/productsApi.js` и `src/api/ordersApi.js`. Подробнее — в `docs/api.md`.

## OrdersProvider и useOrders

`src/context/OrdersContext.jsx`: провайдер расположен выше страниц в `App.jsx`. Создает независимую копию исходных заказов и их позиций. Хук `useOrders()` возвращает `orders` и `createOrder(payload)`.

`createOrder` добавляет заказ в начало и возвращает объект. Отдельные счетчики заказов и позиций начинаются после максимальных ID исходных данных. Статус — `NEW`, приоритет — `MEDIUM`, время создания — ISO. Названия изделий берутся из справочника. В режиме api общий контекст загружает заказы из Java и сохраняет созданный через API заказ для открытия его карточки. Демонстрационные команды планирования к серверным заказам не применяются.

## OrderForm

`src/components/orders/OrderForm.jsx` хранит поля, проверяет их и передает подготовленный объект в `onSubmit`. Болванки и контекст форма не импортирует.

| Параметр | Назначение |
|---|---|
| `products` | Массив изделий: id, title, description |
| `onSubmit(payload)` | Обработка корректного заказа |
| `onCancel()` | Нажатие «Отмена» |
| `isSubmitting` | Блокировка полей и кнопок, текст «Создать…» |
| `submitError` | Сообщение об ошибке создания или null |

Объект для `onSubmit` содержит только `dueDate` (YYYY-MM-DD), `comment` (строка, в том числе пустая) и `items` с числовыми `productId` и `quantity`. Формат пригоден для последующего подключения Java.

## Проверка

1. Отправьте пустую форму: ошибки возле состава и даты, заказ не создается.
2. Добавьте изделие дважды: одна строка, количество 2. Добавьте другое, удалите строки — после последней появится «Добавьте изделия в заказ».
3. Проверьте пустое количество, 0, отрицательное и дробное число; вчерашнюю дату; комментарий из 201 символа. Ошибки видны возле полей, введенные значения сохраняются. Сегодня определяется по локальному времени пользователя.
4. Исправьте значения: сегодняшняя дата и комментарий до 200 символов включительно разрешены. После создания проверьте новый заказ первым в списке, статус «Новый», приоритет «Средний» и счетчик.
5. Создайте еще заказ: номера разные. Перейдите в «Изделия» и обратно — заказы сохраняются. Перезагрузите страницу — снова два исходных заказа.
6. Для проверки блокировки временно передайте в `CreateOrderPage.jsx` параметр `isSubmitting={true}`: поля, добавление, удаление, создание и отмена недоступны. Затем верните `isSubmitting={isSubmitting}`.
7. Для проверки сообщения временно передайте `submitError="Проверка ошибки"`: сообщение видно возле кнопок. Для проверки сбоя при отправке временно добавьте `throw new Error("Проверка")` внутри `try` перед `createOrder(payload)`. Заполните и отправьте форму: перехода нет, значения сохранены, сообщение видно, кнопки снова доступны. Удалите временный throw и повторите — заказ создается.

Искусственной задержки нет, поэтому при обычном создании блокировка может быть незаметна. После проверок верните обычные параметры и удалите временную ошибку.
