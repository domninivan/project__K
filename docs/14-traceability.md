Матрица трассируемости требований

Кейс 22 · Мастер-план · Редакция 0.3 · 16 ноября 2026 года

Документ связывает базовые требования R01–R32 с архитектурой, общим планом работ и приёмочными проверками. Он показывает не только покрытие задачами, но и разрывы между требованиями и текущей реализацией.

Подготовила: Ручкина Алёна Игоревна. Архитектурное ревью: Бульдин Захар Андреевич. Редакция на согласовании; результаты испытаний здесь не заявляются. Источники S1–S9 перечислены в adr/README.docx.

Объём и правила чтения

Must: R01–R13 и условия качества R27–R32. Should: R14–R20. Could: R21–R26. Реализация части Should не меняет приоритет требования и не должна блокировать обязательный сценарий без отдельного решения команды.

З-01–З-29 — номера из общего плана S4. Уточнения к ним ниже являются предложением обновить план, а не заявлением, что чужой документ уже изменён. ДОП-01–ДОП-06 — новые задачи для закрытия конкретных разрывов; часы, сроки и issue-номера не выдумываются.

Разрывы которые нельзя скрывать

R02: в текущем DTO нет контактов клиента. R04: недельная схема не описывает перерывы и исключения по датам. R05: приоритет передаётся, но правило его влияния не определено. R06: onTime не заменяет численную величину опоздания. R11 и R30: не утверждены формат и ревизии обмена.

POST плана в примере Go возвращает только шапку, Java ожидает items и operations. У availability нет вычитания занятости; это не API свободных окон. Отмена Java-заказа пока не отменяет план Go. Складской дефицит не должен становиться условием расчёта без изменения границ проекта.

Управление изменениями

Предложения по З-13, З-14, З-20, З-21 и З-24 исправляют расхождение общего плана с базовыми границами, а не подтверждают изменение утверждённого объёма. Если команда намеренно расширяет систему до материального обеспечения, это необходимо отдельно внести в требования, ADR и оценки.

Ответственный за пересчёт сроков и трудоёмкости — Проценко. Исполнители оценивают свои уточнённые задачи. Старые 116 часов и цепочки зависимостей не считаются актуальными автоматически. Ссылка на issue и фактический commit добавляются при переносе задач в GitVerse.

| T-13 | Рассчитать ≥100 операций на фиксированном наборе и оборудовании. | ≤5 секунд. В протоколе: commit, CPU/RAM, БД, набор, границы замера, число прогонов; не подменять серверный расчёт временем отрисовки. |
| T-14 | Развернуть проект по инструкции на синтетических данных. | Все компоненты запускаются без удаления пользовательских данных; порты и адреса воспроизводимы, seed согласован. |
| T-15 | Проверить GitVerse для сдаваемой ревизии. | Код, миграции, seed, инструкции и документы доступны и привязаны к согласованной версии. |
| T-16 | Получить список изделий и подробности технологии. | Проверены id, название, описание, порядок, типы и нормативы операций; отсутствующее изделие даёт ожидаемую ошибку. |
| T-17 | Два конкурирующих заказа с разным priority при одинаковой доступности. | Порядок расчёта соответствует правилу ДОП-02; одно хранение поля не считается успешной проверкой. |
| T-18 | POST/GET плана через Java; остановить Go; запросить отсутствующий план; смоделировать ошибку Go. | Полные items/operations в обоих ответах; времена со смещением; соответственно 503, 404, 502 по текущему Java handler. |
| T-19 | Два одновременных расчёта на один центр; повторить запрос создания. | Нет пересечений и частичных планов. Повтор соответствует согласованной идемпотентности; нет второго активного резерва по ошибке. |
| T-20 | Сверить один план в Go, Java, таблице, Ганте и файле/1С; затем обновить план. | ID, ревизия и набор операций согласованы; старый отчёт не выдаётся за текущий; новый импорт атомарен. |

Закрытие требования: исполнитель указывает задачу и commit; тестировщик прикладывает протокол; Ручкина обновляет статус строки; Бульдин проверяет архитектурные расхождения. До этого матрица остаётся планом покрытия.

Задачи следующего этапа

Ответственные указаны как предложение для следующего этапа. У каждой задачи один основной исполнитель. Сроки и оценки не назначены; текущие З-01–З-29 и ДОП-01–ДОП-06 не перенумеровываются.

| Код | Исполнитель | Результат |
| --- | --- | --- |
| РАСШ-01 | Бульдин | Java: модель фактов и отклонений, устойчивый ID операции, права работника/начальника, валидация количества и журнал исправлений. |
| РАСШ-02 | Проценко | Страница работника: операции станка, начало/завершение, количество, сообщение о проблеме; состояния ошибки и повторной отправки. |
| РАСШ-03 | Ручкина | Страница начальника и интеграция с Java: план/факт, отклонения, запуск пересчёта, просмотр изменений и подтверждение. |
| РАСШ-04 | Домнин | Go: учёт фактов и простоев, расчёт остатка, сохранение завершённых операций, версия альтернативы и атомарная замена резервов. |
| РАСШ-05 | Бульдин | Контракт Java ↔ Go и интеграция: версии снимков, ключи команд, подтверждение, ошибки конфликта, обработка сетевого сбоя. |
| РАСШ-06 | Домнин | Приёмочные сценарии T-21–T-27, конкурентные и повторные команды, целостность фактов после смены плана. |

Сначала согласуются модель фактов, права и контракты РАСШ-01/05. Интерфейсы РАСШ-02/03 могут разрабатываться на согласованных примерах; сквозная интеграция зависит от Java и Go. РАСШ-06 выполняется после готовности связанного сценария.

Обновление отчёта 1С при смене действующего плана остаётся по ADR-0003 и T-20. Новую задачу разработки 1С в этот этап без изменения требований не добавляем; Корепанова участвует в проверке согласованности отчёта.

Проверки следующего этапа

| Тест | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| T-21 | Работник открывает свой станок и пытается изменить чужую операцию. | Видит разрешённые задания; сервер запрещает чужое изменение независимо от интерфейса. |
| T-22 | Начало, частичное выполнение, завершение; повтор отправки; количество больше планового. | Автор и время сохранены; повтор не удваивает количество; некорректный объём отклонён. Исправление оставляет историю. |
| T-23 | Работник сообщает о поломке или задержке; начальник уточняет причину и срок. | Сводка обновлена, факт и подтверждённое ограничение различимы; неизвестный срок ремонта не подменяется выдуманным. |
| T-24 | Начальник запускает пересчёт после подтверждения отклонения. | Java передаёт актуальные версии плана/фактов, остатки и ограничения; запрос не идёт из React напрямую в Go. |
| T-25 | Станок сломан после 12 из 20 деталей; в плане есть завершённые и не начатые операции. | Завершённые не повторяются; 8 оставшихся переносятся только при технологической допустимости. Нет назначений на недоступный станок и наложений. |
| T-26 | Рассчитать вариант, затем изменить факт или занятость и попытаться подтвердить. | Устаревший/конфликтующий вариант отклонён. Успешное подтверждение атомарно заменяет резервы; нет одновременной двойной занятости. |
| T-27 | Повторить команду после сетевого сбоя, затем прочитать факты и действующий план. | Один результат команды, одна действующая версия. Факты не потеряны и связаны с той же производственной операцией, даже если назначение изменилось. |

Проверки плановые. Для фактической приёмки требуются согласованные контракты, версии кода и протокол. Текущий MVP не считается проваленным из-за отсутствия ещё не включённого расширения.
