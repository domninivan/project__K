ADR 0001 Разделение ответственности Java и Go

Кейс 22 · Мастер-план · Редакция 0.3 · 16 ноября 2026 года

Подготовила: Ручкина Алёна Игоревна. Архитектурное ревью: Бульдин Захар Андреевич.

Статус редакции: на согласовании. В исходной версии решение отмечено как принято; новые уточнения не считаются согласованными без ревью команды.

Связи: R01–R06, R09, R10, R13, R27; A02–A05. Сценарии: UC01, UC02, UC04.

Java хранит заказ и технологию изделия, Go рассчитывает размещение операций во времени. Это разделение сохраняется; описание дополнено фактической моделью заказа и целевой схемой планирования.

Контекст

Клиент создаёт заказ с несколькими позициями. Для расчёта нужны количество каждого изделия, последовательность операций, норматив времени, рабочие центры и календарь. Эти данные имеют разных владельцев; прямое чтение таблиц соседнего сервиса связывало бы их схемы.

Решение

| Компонент | Ответственность |
| --- | --- |
| Java и Java PostgreSQL | Изделия, технология, нормы материалов, заказы и позиции. Валидация заказа, API для React, сборка задания для Go, экспорт плана в 1С. |
| Go и masterplan_go | Рабочие центры, типы операций, недельный календарь, планы и назначенные операции. Поиск свободных окон, расчёт сроков, занятости и плановых показателей. |
| React | Ввод и отображение данных. После интеграции получает их через Java; локальные данные допустимы на этапе разработки интерфейса. |
| 1С | Импорт согласованного файла, контроль повторного импорта, отчёт по плану и загрузке. Себестоимость относится к Should. |

Java передаёт снимок заказа: orderId, earliestStartAt, dueDate, priority, items. В позиции передаются orderItemId, productId, quantity и operations; операция содержит operationId, sequenceNumber, operationType, timePerUnitSeconds. Go не запрашивает технологию у Java.

Границы данных и поведения

ProductionOrder хранит шапку заказа, ProductionOrderItem — позиции. Повторные productId во входном запросе Java объединяет суммированием количества; в БД действует UNIQUE(order_id, product_id). DELETE заказа меняет статус на CANCELLED и не удаляет запись.

Go хранит внешние идентификаторы Java как external_* без межбазовых внешних ключей. Копия количества и срока в плане — снимок расчёта, а не второй справочник заказов. План принадлежит Go, заказ — Java; их статусы нельзя считать одним и тем же полем.

Длительность операции равна quantity × timePerUnitSeconds. В текущей спецификации операция неделима, позиции могут идти параллельно, а операции одной позиции — только последовательно. Выбирается подходящий активный центр с самым ранним окончанием. Это целевое поведение Go, а не подтверждение завершённой реализации.

Альтернативы и последствия

Единый backend упростил бы транзакции, но убрал бы принятую границу расчётной подсистемы. Общая БД с взаимной записью сервисов облегчила бы доступ к данным, но создала бы зависимость от чужих миграций. Сохраняем два сервиса и обмен по контракту.

Преимущество — независимая проверка алгоритма и развитие подсистем. Цена — сетевые ошибки, необходимость согласования контрактов и согласованной отмены заказа и плана. Общей транзакции PostgreSQL между Java и Go нет.

Что остаётся согласовать и проверить

Передача priority уже предусмотрена, но правило влияния приоритета на очередь расчёта не определено. R05 нельзя считать закрытым только потому, что поле сохраняется. Проверка складских остатков и дефицита не является условием запуска планировщика в базовом объёме.

Отмена Java-заказа пока не вызывает отмену плана Go. Освобождение мощности относится к R15 и требует отдельной интеграции. Контакты клиента из R02 отсутствуют в описанной текущей модели заказа — это открытый разрыв требований.

Проверки: T-01, T-03, T-05, T-16, T-17, T-19. Источники: S1–S4, S7–S9 в adr/README.docx.

Расширение после MVP Учёт выполнения

Редакция 0.3 учитывает предложенные страницы работника и начальника цеха. Детальное решение — ADR-0007. Это следующий этап проекта; наличие этих функций в текущей реализации не заявляется.

| Компонент | Дополнительная ответственность |
| --- | --- |
| React | Работник видит операции закреплённого за ним станка и отмечает выполнение. Начальник цеха видит сводку, задержки и сообщения о поломках. |
| Java | Хранит факты выполнения, автора и время сообщения, выполненное количество, причины отклонений. Проверяет права и собирает запрос перепланирования. |
| Go | Хранит плановые назначения и ограничения доступности ресурсов. Получает согласованный снимок фактов и пересчитывает оставшуюся работу. |
| Начальник цеха | Проверяет сведения, уточняет недоступность оборудования, запрашивает пересчёт и подтверждает новый вариант плана. |

Фактическое выполнение и плановое назначение — разные данные. Выполнение не удаляется и не переписывается при смене плана. Связь должна переживать замену scheduledOperationId: предлагается устойчивый идентификатор производственной операции, отдельный от идентификатора её назначения на станок.

Java остаётся источником фактов, Go — источником плановых назначений. Подтверждённые ограничения доступности Java передаёт в Go через согласованный API. Перепланирование не предполагает прямого изменения таблиц Go из Java.

Связи расширения: R33–R39, A01–A05; существующие R14, R15, R17, R18. Новые номера предварительные и требуют внесения в общий реестр требований. Владелец архитектурного согласования — Бульдин.
