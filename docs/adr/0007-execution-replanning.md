ADR 0007 Выполнение работ и перепланирование

Кейс 22 · Мастер-план · Редакция 0.3 · 16 ноября 2026 года

Статус: предложено. Этап: расширение после MVP. Ответственная за документ — Ручкина Алёна Игоревна; архитектурное ревью — Бульдин Захар Андреевич.

Основание: новая идея команды — страницы работника и начальника цеха, фиксация выполненных операций и корректировка плана по задержкам и поломкам. Функциональность ещё не заявлена реализованной. Дополнения связаны с R14, R15, R17, R18 и предварительными R33–R39; архитектура A01–A05.

Контекст и решение

Планировщик строит ожидаемый ход производства. Для реакции на отклонения нужны факты: что начато и закончено, сколько выполнено, что остановлено и когда ресурс снова станет доступен. Эти сведения поступают от работников; начальник цеха проверяет их и управляет пересчётом.

| Роль | Возможности страницы |
| --- | --- |
| Работник | Список операций назначенного станка: заказ, изделие, операция, плановые сроки и количество. Действия: начать, отметить выполненное количество, завершить, сообщить о задержке или поломке. |
| Начальник цеха | Сводка план/факт по заказам и станкам, незавершённая работа, отклонения и простои. Уточнение причин и прогноза восстановления, запуск пересчёта, сравнение нового варианта и подтверждение. |

Обзор начальника строится из данных, накопленных системой. На первом этапе это сведения по доступному ему цеху; обзор всего предприятия требует отдельного определения состава цехов и прав. Работник не получает право менять общий календарь или подтверждать новый план.

Границы ответственности

Java принимает факты, проверяет права, хранит журнал изменений и готовит снимок для Go. Go рассчитывает оставшуюся работу и владеет плановыми назначениями и резервами. React обращается только к Java. 1С не является обязательным посредником перепланирования; обновление отчётов выполняется по ADR-0003.

Фактические данные и правила пересчёта

| Объект | Что требуется фиксировать |
| --- | --- |
| Выполнение операции | Устойчивая ссылка на производственную операцию, заказ/позиция, станок, работник, фактическое начало/завершение, выполненное количество, состояние и версия записи. |
| Отклонение | Причина, момент возникновения и регистрации, автор, комментарий, затронутая операция/станок, прогноз задержки или восстановления. |
| Запрос пересчёта | Ключ команды, версия исходного плана, версия снимка фактов, момент пересчёта, оставшиеся объёмы и ограничения ресурсов. |
| Результат | Версия нового варианта, изменённые назначения, прогноз сроков и опозданий; ссылка на исходный план и снимок фактов. |

Это проект состава данных, а не описание существующих DTO. Статус выполнения операции отделяется от статуса плана PROPOSED/ACCEPTED/REJECTED/CANCELLED. Идентификатор назначения scheduledOperationId не используется как единственный постоянный ключ факта.

Завершённая операция остаётся в истории и не выполняется повторно. Для выполняющейся операции нельзя автоматически переносить всю исходную партию. Начальник уточняет остаток, состояние остановленной работы и допустимость переноса. Не начатые операции допускают перераспределение между технологически подходящими центрами.

Пример: выполнено 12 из 20 деталей, станок сломан. Оставшиеся 8 можно запланировать на другом станке только при подтверждении, что 12 деталей завершили эту операцию и остаток технологически переносим. Для неделимой или непрерывной операции такой перенос может быть невозможен — нужно отдельное правило.

При неизвестном сроке ремонта станок недоступен для новых назначений до уточнения в пределах горизонта расчёта. Если подходящего ресурса нет, система сообщает причину невозможности назначить остаток; недостоверную дату завершения не подставляет.

Подтверждение версии и последствия

Запуск пересчёта не заменяет действующий план. Go строит альтернативу, начальник видит новые сроки и изменения. Подтверждение проходит через Java с ожидаемой версией; Go повторно проверяет ограничения и атомарно меняет резервы. Устаревший или конфликтующий вариант не активируется.

Для черновика перепланирования нужен отдельный режим резервирования: старый план продолжает занимать ресурсы, а альтернатива не создаёт двойного резерва. Текущий статус PROPOSED резервирует мощность по Go-спецификации, поэтому переиспользовать его без уточнения протокола нельзя.

Альтернативы

Автоматический пересчёт после каждой отметки быстрее реагирует, но может постоянно менять задания работников. Выбран первый вариант с запуском и подтверждением начальником. Ручная передача сведений в Go проще технически, но создаёт риск неполного снимка; подготовку данных выполняет Java.

Последствия и границы этапа

Появляется сравнение плана с фактом и возможность учитывать реальные простои. Цена — роли доступа, журнал фактов, версии и дополнительный контракт Java ↔ Go. Телеметрия станков, автоматическое выявление поломок, зарплата, табель и полноценная MES в это расширение не включаются.

Перед реализацией согласовать закрепление работников за станками, единицы выполненного количества и правила исправления ошибочных отметок; перенос незавершённой партии; горизонт расчёта; статус черновика и замену резервов; полномочия начальника. Один работник на один станок навсегда не предполагается.

Трассируемость и критерий готовности

R33–R35: страницы и журнал фактов, задачи РАСШ-01–РАСШ-03, T-21–T-23. R36–R39: запрос, пересчёт, подтверждение и согласованность, РАСШ-04–РАСШ-06, T-24–T-27. Эти проверки планируются для следующего этапа и не подменяют приёмку текущего MVP.
