ADR 0006 Бизнес модули Java

Кейс 22 · Мастер-план · Редакция 0.3 · 16 ноября 2026 года

Подготовила: Ручкина Алёна Игоревна. Архитектурное ревью: Бульдин Захар Андреевич.

Статус редакции: на согласовании. В исходной версии решение отмечено как принято; новые уточнения не считаются согласованными без ревью команды.

Связи: R01, R02, R05, R13; A02, A04. Сценарии: UC01, UC02.

Java организована по бизнес-модулям product, order и planning. Внутри модуля разделены HTTP-контроллеры, сервисы, DAO, модели, DTO и преобразователи. Межмодульное обращение проходит через сервис, а не через чужой DAO.

Структура и ответственность

| Модуль | Содержание |
| --- | --- |
| product | Product, ProductOperation, ProductMaterialRequirement; отдельные DAO и ProductService. ProductDetails — внутренняя модель, не entity. |
| order | ProductionOrder, ProductionOrderItem, DAO, сервис, DTO, mapper и controller. Создание, чтение и логическая отмена заказа. |
| planning | PlanningController, PlanningService, GoPlanningClient и реализация на RestClient, интеграционные DTO, PlanningMapper, исключения и обработчик ошибок. |
| Общий код | Выносить в common только действительно общие элементы. Наличие и состав такого пакета в актуальном коде отдельно не подтверждены. |

ProductDetails объединяет Product, List<ProductOperation> и List<ProductMaterialRequirement>. Product не обязан иметь @OneToMany на операции и материалы: ProductService собирает подробности отдельными DAO. Для расчёта планирования getProductOperations(productId) получает только технологические операции без материалов.

ProductionOrderService сохраняет доступ к ProductService.getProduct(id), поскольку он нужен для создания заказа. PlanningService загружает заказ через сервис order, технологию — через сервис product, затем собирает PlanningRequest. PlanningMapper не обращается ни к DAO, ни к сервисам.

Правила слоёв и проверка решения

Controller отвечает за HTTP и DTO. Service выполняет бизнес-действие и задаёт границы транзакции. DAO отвечает за запросы и сущности. Mapper преобразует уже загруженные модели. GoPlanningClient занимается транспортом, а интерпретация ошибок и сценарий вызова находятся в planning-сервисе и обработчике исключений.

Альтернативы и последствия

Общие пакеты controllers/services/repositories разделили бы код только по техническим слоям, затрудняя поиск всего сценария заказа. Сервис на каждую таблицу создал бы лишние интерфейсы. Выбранные модули отражают бизнес-функции, но требуют контроля циклических зависимостей и дисциплины при выносе общего кода.

Сохраняется направленность зависимостей: order использует product; planning использует order и product. Модули product и order не должны зависеть от HTTP-клиента Go для обычного чтения своих справочников и заказов.

Практические проверки

Проверить, что ProductDetails находится в product.model; DTO контроллера не используются как результат обычного метода DAO; mapper не делает запросов; планирование получает операции через ProductService, а не загружает нормы материалов без необходимости.

Проверить чтение заказа после завершения сервисной транзакции: позиции и Product должны быть доступны для преобразования в ответ. Проверить исключение для отсутствующего изделия через ProductExceptionHandler и отдельную обработку ошибок планирования.
