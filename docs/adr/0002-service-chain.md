ADR 0002 Взаимодействие React Java и Go

Кейс 22 · Мастер-план · Редакция 0.3 · 16 ноября 2026 года

Подготовила: Ручкина Алёна Игоревна. Архитектурное ревью: Бульдин Захар Андреевич.

Статус редакции: на согласовании. В исходной версии решение отмечено как принято; новые уточнения не считаются согласованными без ревью команды.

Связи: R01, R02, R05, R07–R10, R13, R28; A01–A03. Сценарии: UC01–UC05.

React обращается к Java. Java собирает производственное задание, вызывает внутренний Go API и возвращает результат интерфейсу. Прямые вызовы Go из React не добавляются.

Решение и текущее состояние

Локальные адреса: Java — порт 8080, Go — порт 8081. Java читает go.base-url=http://localhost:8081. Для отдельных контейнеров адрес заменяется на имя Go-сервиса в общей Docker-сети.

| Java метод | Go маршрут | Состояние |
| --- | --- | --- |
| createPlan(request) | POST /api/plans | Java-клиент реализован; полноценный Go endpoint ещё требуется. |
| getOrderPlan(orderId) | GET /api/plans/orders/{orderId} | Java-клиент реализован; полный ответ Go требуется согласовать. |
| getWorkCenters() | GET /api/work-centers | Java-клиент реализован; проверить совпадение пути с работающим Go. |

Цепочка Java: PlanningController → PlanningService → GoPlanningClient → RestClient. Сервис загружает заказ и операции через сервисы модулей order и product. MapStruct преобразует готовые данные; HTTP-транспорт и доступ к БД в mapper не размещаются.

Java использует полный ProductionPlanResponse для создания и чтения плана: planId, orderId, plannedStartAt, plannedFinishAt, onTime, status, items. Каждая позиция содержит operations с назначенным центром и временными границами. Время передаётся с UTC-смещением, Java использует OffsetDateTime; бизнес-пояс — Europe/Moscow.

Известное расхождение контракта

В S8 пример POST возвращает только шапку, а GET — подробный план и другой Java-тип. Цель согласования — полный ответ с items и operations для обоих методов, как в текущем Java-клиенте. Поле dueDate есть в примере Go, но не перечислено в текущем Java DTO: оно должно быть явно согласовано, без предположения о его наличии в Java.

Следующие методы и обработка ошибок

| Метод Go из спецификации | Назначение |
| --- | --- |
| GET /api/work-centers/{id}/schedule | Недельный шаблон работы. |
| PUT /api/work-centers/{id}/schedule | Полная замена шаблона; обработку конфликтов с уже назначенными операциями нужно определить. |
| GET /api/work-centers/{id}/availability | Календарные рабочие интервалы на даты; занятость заказами не вычитается. |
| GET /api/schedule | Занятые интервалы, сгруппированные по рабочим центрам, для общего Ганта. |
| POST /api/plans/{planId}/accept и /reject | Подтверждение и отклонение плана; расширение R15. |
| POST /api/plans/orders/{orderId}/cancel | Логическая отмена активного плана заказа; расширение R15. |

Эти методы описаны в Go-спецификации, но их Java-клиенты ещё не заявлены реализованными. Публичные маршруты PlanningController в источнике не перечислены: их следует брать из кода и зафиксировать в контракте React ↔ Java, не копировать автоматически внутренние Go URL.

Текущая обработка Java: Go недоступен — 503; необработанная ошибка Go 4xx/5xx — 502; 404 при чтении плана — 404. Таймауты, единое тело ошибки, идемпотентность POST и повторные запросы необходимо согласовать. Повторять создание плана автоматически до определения идемпотентности нельзя.

Альтернативы и последствия

Прямой React → Go сократил бы один переход, но вынес бы внутренний контракт в интерфейс. Обратные запросы Go → Java связали бы расчёт с доступностью Java. Выбранная цепочка оставляет один внешний API и самостоятельный расчёт по переданному снимку; Java становится дополнительной точкой отказа.

Раннее задание Go использовало /api/v1/work-centers; новые спецификации используют /api/work-centers. Проверка и выравнивание маршрута обязательны. Проверки: T-02, T-07–T-10, T-18. Источники: S3, S7–S9.

Расширение после MVP Обратная связь из цеха

Для страниц работника и начальника цеха сохраняется маршрут React → Java → Go. Сведения о ходе работ сначала сохраняются в Java. Сборка снимка фактов и вызов Go выполняются Java; пользователь не формирует транспортный JSON вручную.

| Шаг | Действие и результат |
| --- | --- |
| 1 Факт | Работник отмечает начало, завершение, количество или проблему. Java проверяет назначение и сохраняет запись с автором и временем. |
| 2 Отклонение | Начальник видит план и факт, подтверждает причину, уточняет период недоступности станка и решение по незавершённой работе. |
| 3 Пересчёт | Java передаёт Go исходную версию плана, версию фактов, завершённые и выполняющиеся операции, оставшийся объём и ограничения ресурсов. |
| 4 Предложение | Go возвращает новый вариант плана, новые сроки, опоздания и изменённые назначения. Он ещё не является действующим заданием работнику. |
| 5 Подтверждение | Начальник подтверждает вариант через Java. Go проверяет актуальность версий и атомарно заменяет действующие резервы; React получает обновлённые назначения. |

Конкретные URL, DTO и таблицы расширения пока не реализованы и в этом ADR не выдаются за существующий API. Команды должны иметь ключ повторного запроса и ожидаемую версию. При сетевом сбое система проверяет результат предыдущей команды, а не создаёт новый пересчёт вслепую.

Если после расчёта пришёл новый факт или изменился календарь, подтверждение устаревшего варианта отклоняется. Новая версия должна учитывать актуальные данные. Для первоначального PROPOSED в текущей Go-спецификации сохраняется резервирование; правила черновика перепланирования проектируются отдельно, чтобы не удвоить занятость старого и нового планов.

Связи: ADR-0007, R33–R39, R14, R15, R17, R18; проверки T-21–T-27. Название статуса нового черновика и способ передачи подтверждённых простоев согласуются в будущей задаче РАСШ-05.
