ADR 0005 Хранилище и планировщик Go

Кейс 22 · Мастер-план · Редакция 0.3 · 16 ноября 2026 года

Подготовила: Ручкина Алёна Игоревна. Архитектурное ревью: Бульдин Захар Андреевич.

Статус редакции: на согласовании. В исходной версии решение отмечено как принято; новые уточнения не считаются согласованными без ревью команды.

Связи: R03–R06, R09, R10, R13, R27–R29; A03, A05. Сценарии: UC02, UC04; UC05 только расширение.

Go использует Gin, pgx и отдельную PostgreSQL-БД masterplan_go. Целевая схема содержит шесть таблиц. Данные календарной доступности и свободные окна вычисляются; отдельные таблицы free_slot и availability не создаются.

Владение данными

| Таблица | Назначение и ключевые ограничения |
| --- | --- |
| work_center | Оборудование: id, уникальный code, title, active. В целевой спецификации заполняется seed; API создания не требуется. |
| work_center_operation_type | Поддерживаемые типы; PK(work_center_id, operation_type). |
| work_center_schedule | Недельный шаблон; PK(work_center_id, day_of_week), день 1–7, start_time < end_time. Нет строки — выходной. |
| production_plan | План заказа: external_order_id, due_date, priority, сроки, on_time, status, created_at, updated_at. |
| production_plan_item | Позиция плана: external_order_item_id, external_product_id, quantity > 0; UNIQUE(production_plan_id, external_order_item_id). |
| scheduled_operation | Операция: external_operation_id, sequence_number > 0, operation_type, work_center_id, start_at < finish_at. |

Внешние ID Java не являются FK. Внутренние ссылки Go проверяются FK. Нужны индексы по external_order_id, связям плана и позиций, а также scheduled_operation(work_center_id, start_at, finish_at). Миграции Go ведёт Домнин; Ручкина согласует общие тестовые данные. Java не записывает таблицы Go.

Рабочие и свободные интервалы

GET availability возвращает календарную доступность без вычитания заказов. Планировщик вычисляет свободное время отдельно: рабочие интервалы минус операции планов PROPOSED и ACCEPTED. REJECTED и CANCELLED не занимают оборудование. Моменты времени хранятся как TIMESTAMPTZ; календарь разворачивается в Europe/Moscow.

Сохранение плана и ограничения первой версии

План, позиции и операции сохраняются атомарно. Перед фиксацией выбранные ресурсы блокируются и пересечения проверяются повторно. Все команды изменения занятости должны соблюдать один протокол блокировки. Индекс по времени ускоряет поиск, но сам по себе не запрещает наложение операций.

Предлагается сравнивать интервалы как [start, finish): окончание одной операции может совпадать с началом следующей. Порядок блокировки центров, поведение при конфликте, повторный POST и выбор активного плана заказа должны быть закреплены в спецификации до интеграционной приёмки.

Разрывы требований

| Ограничение спецификации | Необходимое действие |
| --- | --- |
| Один интервал на день недели | Не покрывает перерыв внутри смены, исключения по датам и праздники. Расширить календарь или согласовать изменение базового R04; нельзя объявлять его полностью выполненным. |
| Неделимая операция | Для операции длиннее любой смены нужен конечный отказ с причиной, а не бесконечный поиск. Горизонт поиска и предельные значения ещё согласуются. |
| priority только передаётся | Определить его влияние на очередь заказов и проверить R05. Сохранение поля не доказывает учёт приоритета. |
| Смена шаблона календаря | Определить отказ или перепланирование при конфликте с назначенными операциями; молча оставлять их вне рабочего времени нельзя. |
| Несколько планов одного заказа | Согласовать единственность активного плана, повтор команды, переходы статусов и правило GET по orderId. |

Альтернативы и последствия

Общее хранилище с Java упростило бы связи, но нарушило владение данными. Хранение готовых свободных окон потребовало бы их синхронизации при каждом изменении плана. Отдельная БД и вычисляемые окна сохраняют независимость схемы; цена — необходимость строгих контрактов и конкурентных проверок.

При невозможности уложиться в dueDate алгоритм ищет ближайшее достижимое завершение и возвращает onTime=false. Численное опоздание R06 ещё нужно определить. Шесть тестовых станков из сценария S9 отличаются от начального seed первого задания: использовать отдельный именованный набор, не смешивать ID.

Проверки: T-03–T-06, T-09, T-10, T-13, T-17, T-19. Источники: S1, S4, S7–S9.

Расширение после MVP Пересчёт по фактам

По ADR-0007 Go будет получать фактическое состояние производства из Java. Завершённые операции не назначаются повторно. Выполняющиеся операции сохраняют ограничения текущего исполнения; перенос остатка допускается только после фиксации остановки и технологической допустимости переноса.

Поломка задаёт недоступность ресурса с началом и ожидаемым окончанием. Если окончание неизвестно, ресурс исключается из назначения в пределах горизонта расчёта до уточнения. Истечение прогнозного срока ремонта само по себе не означает подтверждённое восстановление станка.

Задержка работающей операции меняет прогноз освобождения станка. В этом случае недостаточно передать только число выполненных деталей: могут потребоваться оценка остаточного времени, состояние партии и ограничения технологии.

Текущих шести таблиц и недельного шаблона недостаточно для всего расширения. Потребуются модель исключений доступности, устойчивые ссылки на производственные операции и версии пересчёта. Конкретная схема будет отдельной миграцией после согласования; здесь новые таблицы не объявляются существующими.

При построении альтернативы активный план продолжает определять занятость. Альтернатива не должна резервировать те же интервалы второй раз. При подтверждении Go в транзакции проверяет ресурсные конфликты и актуальность, заменяет прежние резервы и активирует новый вариант. При конфликте действующий план остаётся неизменным.
