1. Результат актуализации

Базовый план охватывает приём заказа, расчёт производственного плана, отображение сроков и загрузки, файловый обмен и отчёт в 1С. Новые страницы работника и начальника цеха выделены в следующий этап. Они не включены в текущую оценку и срок сдачи.

| Область | Что учитывать в плане |
| --- | --- |
| Java | API изделий и заказов уже описаны как реализованные. З-10 теперь проверка и доводка. GoPlanningClient имеет три метода; З-12 — согласование и интеграционная проверка, а не написание с нуля. |
| Go | Шесть таблиц целевой схемы и API описаны, но завершение планировщика не подтверждено. Пять блокеров и расхождения контракта остаются входными условиями приёмки. |
| React | Первый этап — макет; второй — локальное создание заказа с показом в списке; третий — подключение Java. В навигации «Заказы» и «Изделия»; создание открывается кнопкой, маршрут /orders/new сохраняется. |
| 1С | Базовый обмен — файл, экспортируемый Java. Материалы, дефицит и стоимость отделены как Should и не блокируют расчёт производственного плана. |
| Архитектура | React → Java :8080 → Go :8081. Java хранит изделия и заказы; Go — ресурсы, календарь и планы в masterplan_go. Прямого доступа к чужой БД нет. |

Оценки и срок

Предлагаемая оставшаяся работа: 123 человеко-часа обязательного объёма и 16 часов выбранных Should-задач. Это новая оценка для обсуждения с исполнителями, а не фактически затраченное время. Оценка не включает неограниченное исправление дефектов и расширение после MVP.

При исходном режиме 2 часа в день, понедельник–четверг, приведённый ресурсный график заканчивается 23 декабря. Целевая сдача 20 декабря сохраняется как ограничение. Вариант с дополнительными пятницами у Бульдина и Домнина позволяет назначить демонстрацию на 17 декабря; увеличение доступности требует согласования команды.

5. Критический путь и управление сроком

Технический критический путь по оценкам обязательных задач, без ограничения ресурсов: З-01 → З-02 → З-15 → З-16 → ДОП-03 → З-25 → З-26 → З-27 → З-29. Длина — 36 человеко-часов последовательной работы. Часы разных участников в этой цепочке нельзя автоматически перевести в календарные дни.

Ресурсное ограничение меняет результат: у Бульдина 37 ч, у Домнина 38 ч обязательных работ. Они выполняют несколько ветвей, и следующие задачи ждут одновременно готовности интерфейса, ролей, алгоритма и проверок. Свободные часы других участников не заменяют их автоматически.

| Б. Дополнительная доступность — предложение | Бульдин и Домнин могут работать ещё по 2 ч в пятницу, до 10 ч/неделю; остальные — до 8. Тот же объём 123 ч, демонстрация 17.12. Это перераспределение часов, не увеличение оценки. |
| В. Согласованное изменение объёма | Если дополнительные слоты недоступны, команда пересматривает оценки, порядок и объём. Must нельзя молча удалить ради даты: изменение R04/другого требования фиксируется отдельно. |

18–20 декабря во втором варианте — календарный буфер до сдачи, но не обещанные рабочие часы на дефекты. Should-задачи 16 ч и расширение после MVP не занимают этот буфер без нового решения. Подтверждение отдельных уже завершённых работ может сократить график; неподтверждённая готовность формы — увеличить.

Главные риски и действия

| Риск | Владелец и действие |
| --- | --- |
| Неполный контракт плана | Бульдин: согласовать полный ответ с items/operations, публичные Java-маршруты, путь work-centers, формат времени и ошибок. Не копировать Go URL во frontend. |
| Двойной резерв и зависание расчёта | Домнин: закрыть повторные команды, блокировки, единственность активного плана, предел поиска и длинные операции до приёмки. |

| Расширение выросло внутри MVP | Бульдин: отдельно утвердить новый этап по ADR-0007; Проценко обновляет план только после оценки задач. |

6. Следующий этап: выполнение и перепланирование

Основание — ADR-0007 и матрица трассируемости Ручкиной, редакция 0.3. Требования R33–R39 и номера UC09–UC11 предварительные; приоритеты и даты требуют согласования. Новый этап развивает R14, R15, R17, R18 и не меняет автоматически их текущие приоритеты.

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Работник | Видит доступные ему операции назначенного станка, отмечает начало, выполненное количество, завершение и проблему. Права проверяет Java. |
| Начальник цеха | Видит план/факт, задержки и простои по своему цеху, уточняет причины и недоступность оборудования, запускает расчёт и подтверждает новый вариант. |
| Java | Хранит факты с автором и временем, защищает от повторной записи, собирает согласованный снимок данных для Go. |
| Go | Пересчитывает оставшуюся работу. Завершённые операции не назначаются снова; недоступный станок исключается. Подтверждение проверяет актуальность и атомарно заменяет резервы. |

| Код | Исполнитель | Результат / входные условия |
| --- | --- | --- |
| РАСШ-01 | Бульдин | Модель фактов, стабильный ID операции, права, количество и история исправлений; сначала согласовать правила с командой. |
| РАСШ-02 | Проценко | Страница работника; макет после согласования РАСШ-01/05, полноценное подключение после готовности Java. |
| РАСШ-03 | Ручкина | Страница начальника, план/факт, отклонения, запуск и подтверждение; интеграция после РАСШ-01/04/05. |
| РАСШ-04 | Домнин | Остаток работ, простои, версии плана и атомарная смена резервов; по модели и контракту РАСШ-01/05. |
| РАСШ-05 | Бульдин | Контракт и Java-интеграция: снимки, версии, ключи команд, конфликт и сбой; контракт готовится до реализации РАСШ-04. |
| РАСШ-06 | Домнин | Приёмка T-21…T-27 после подключения страниц и backend; каждый разработчик исправляет свой компонент. |

РАСШ-05 разделяется на раннее согласование контракта и последующую реализацию интеграции. Это устраняет ложный цикл зависимостей. Для всех шести задач: трудозатраты не оценены, даты не назначены, в 123/139 ч они не включены.

7. Приёмка расширения и сопровождение плана

| Проверки | Критерий результата |
| --- | --- |
| T-21, T-22 / R33, R34 | Работник не может менять чужие операции; повтор отправки не удваивает количество. Ошибочные значения отклоняются, исправление оставляет историю. |
| T-23, T-24 / R35, R36 | Отклонение видно начальнику. Java передаёт актуальный снимок фактов и ограничений; React не вызывает Go напрямую. |
| T-25 / R37 | Из 20 деталей выполнены 12: перенос возможен только для оставшихся 8 и только если технология допускает. Завершённая работа не повторяется. |
| T-26 / R38 | Устаревший либо конфликтующий вариант не подтверждается. Новый план не резервирует мощность второй раз поверх старого. |
| T-27 / R39 | После сбоя и повторной команды факты сохранены, результат не дублируется, действующая версия однозначна. |

Если срок ремонта неизвестен, станок исключается из новых назначений в пределах горизонта расчёта до уточнения. Прогноз окончания ремонта не равен подтверждению восстановления. Работник не меняет календарь производства и не утверждает новый план.

Обзор всего предприятия требует определения нескольких цехов и прав доступа; начальный экран начальника описывает доступный ему цех. Телеметрия станков, зарплата, табели и полноценная MES не включены. Отчёт 1С синхронизируется с действующей версией по ADR-0003; участие Корепановой — сверка отчёта.

Порядок актуализации

После ревью Проценко вносит остаток часов, статус, фактические даты и зависимости. Закрытие задачи подтверждают результат и проверка в GitVerse. Бульдин согласует изменение объёма/сроков; Ручкина синхронизирует номера задач в матрице; Домнин — проверки; Корепанова — общий реестр изменений и отчёт о ходе работ.

При изменении требований одновременно обновляются MoSCoW, границы системы и Use Case; архитектуру C4 согласует Бульдин. Для этой редакции предлагается новый запрос на изменение по ADR-0007; номер назначается в общем реестре, чтобы не пересечься с уже существующими ЗИ.
